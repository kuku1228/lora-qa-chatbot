## 1. 一句话看懂这个项目

> 我们拿一个"什么都会一点但说话不够专业"的通用大模型（Qwen2-7B），
> 用 **2 万条中文问答数据**做了 **LoRA 轻量微调**，让它说话变得**简洁、准确、专业**；
> 然后再给它装上 **LangGraph Agent**，让它不仅能回答，还能**自己调用工具**（算数、查时间、抓网页），
> 最后用 **vLLM** 把它部署成线上服务，在浏览器里就能对话。

简单说三层：

```
数据层  →  模型层  →  Agent 层
2万条   →  LoRA微调 →  ReAct推理
中文指令   的Qwen2    + 工具调用
           7B         → 网页可对话
```

## 3. 模型架构详解（零基础）

### 3.1 大语言模型（LLM）是什么

想象一个**特别会接话的学霸**。你给它一句话，它通过"预测下一个词"的方式一个字一个字地往下接：

```
输入：今天天气很……
模型内部预测：下一个词最可能是"好"（概率 60%）/ "冷"（30%）/ 其它
输出：好
```

它见过的文字比任何人一辈子读的都多（几十亿甚至上万亿字），所以"接话"接得非常好——这就是**预训练（pretrain）**。

- **Transformer**：目前所有主流大模型的结构，核心是**注意力机制**——模型读一句话时，会"注意"到句中每个词跟其它词的关系（比如"苹果"后面更容易接"好吃"还是"手机"，取决于上下文）。
- **Qwen2-7B**：阿里巴巴开源的一个模型。"7B" = 70 亿个参数。参数就是模型里成千上万个数字，是模型"学到的东西"的载体。70 亿个数字 ≈ 14GB 存储（fp16 格式）。
- **Instruct**：后缀表示它经过"指令微调"，即专门训练过"听懂人的指令并照做"。

### 3.2 为什么还要微调（fine-tune）

预训练模型"什么都知道一点"，但**说话风格不可控**：

| 问题 | 例子（真实发生在原版模型上） |
|---|---|
| 回答发散 | 问 A 能扯到 C、D、E |
| 逻辑啰嗦 | 结论前铺垫一大堆 |
| 术语不准确 | 问"什么是 LoRA 微调"→ 原版答成"LoRa 无线通信协议"（那是物联网技术，完全错了！） |

**微调** = 用一批"标准答案"继续训练模型，让它**学会你想要的那个说话风格**。
我们用了 2 万条"简洁、准确、专业"风格的中文问答数据来教它。

### 3.3 LoRA：只训练 1% 参数的微调（项目核心）

直接"全量微调"70 亿参数有三大问题：**显存要 70GB+、容易过拟合、烧钱**。

**LoRA（Low-Rank Adaptation，低秩适配）** 的思路是：

> 模型原来就有 W（预训练权重，冻结不动）。
> 我们不去动 W，只在它旁边**并联**两个小矩阵 A 和 B（很小，比如 8 行 × 4096 列），
> 训练时**只更新 A、B**，完成后模型等效权重 = W + B·A。

示意图（类比：不动整栋楼，只在墙上加两小层改造）：

```
       原来： 输入 ──→ [ W ] ──→ 输出        W：70亿参数，冻结 ❄️

   LoRA后： 输入 ──→ [ W ] ──→ 输出 ─┐
                     └─→ [ A ] → [ B ] ─┘    A、B：约 700万参数，训练 🔥
```

- **r（秩）= 8**：控制 A、B 矩阵的大小。r 越大能力越强但越容易过拟合；8 是工业界常用值。
- **alpha = 16**：缩放系数，实际增量 = (alpha/r)·BA = 2·BA。
- 训练完后，A·B 的增量可以**合并回 W**，推理时完全不增加耗时。

**结果**：只训练了 **<1%** 的参数（约 700 万 / 70 亿），显存需求大幅降低，普通 24GB 显卡就能训。

### 3.4 4bit 量化：显存直降 70% 的关键

正常模型权重用 fp16（16 位，2 字节/参数），7B ≈ 14GB。
**4bit 量化**把每个参数压到 4 位（0.5 字节），7B ≈ 3.5GB，显存需求直降约 70%。

本项目用的方案：
- **NF4 格式**：比普通 4bit（fp4）精度更高的一种量化格式；
- **双重量化（Double Quant）**：连"量化用的缩放常数"也再量化一次，再省一点；
- **计算仍走 bf16**：权重存储用 4bit 省显存，计算时临时转回高精度，精度损失可控。

### 3.5 训练时数据是怎么"喂"给模型的

数据是一行行的 JSON（`data/train.jsonl`）：

```json
{"instruction": "什么是过拟合？", "input": "", "output": "过拟合是指模型在训练数据上表现好、但在新数据上表现差的现象……"}
```

训练脚本把它拼成模型的"聊天模板"（Qwen2 的 Chat 格式）：

```
<|im_start|>system
你是专业的中文问答助手。请直接、准确、简洁地回答问题。
<|im_end|>
<|im_start|>user
什么是过拟合？
<|im_end|>
<|im_start|>assistant
过拟合是指……
<|im_end|>
```

然后 tokenizer 把这段文字切成一个个 **token**（词元）变成数字，模型通过"预测下一个 token"来学习——它要做的就是**尽可能预测得准**，预测不准就更新 A、B 两个小矩阵，直到 loss（损失，越小越好）收敛。

### 3.6 怎么证明微调有效（评估）

`3_evaluate.py` 做两件事：
1. **PPL（困惑度）**：衡量模型对评估语料的"意外程度"，越低越好。同一批 100 条数据，微调后 PPL 应显著下降；
2. **同题对比**：6 个问题，分别让"原版模型"和"微调后模型"回答，人工对比。实测微调后回答篇幅压缩约 60%、术语从错误纠正为正确。

## 4. Agent 架构详解（零基础）

### 4.1 Agent 是什么

微调后的模型依然只是"会接话"——你问它"现在几点？"，它只能瞎猜一个时间，因为它**不会查**。

**Agent（智能体）** = 给模型装上"手和眼"：它能**决定调用工具**（查时间、算数、抓网页），看到结果后**继续推理**，直到给出答案。

比喻：
- 普通模型 = 只会背书的同学 📖
- Agent = 会查字典、按计算器、上网找资料的助理 🧰

### 4.2 LangGraph：把推理流程画成一张图

**LangGraph** 是 LangChain 官方的一个库，让你用"**图**"的方式来编排 AI 流程。图 = 节点 + 边 + 条件分支，本质是一个**状态机**。

本项目 Agent 的图（`agent_react.py`）：

```
        ┌──────────────────────────────┐
        ▼                              │
   [model 模型节点]                    │
        │                              │
        ▼                              │
   [route 条件路由]  ── 判断模型输出 ──┤
        │                              │
   ┌────┴─────┐                        │
   │ 是工具指令│ 否（直接回答）          │
   ▼          ▼                        │
 [tool 工具节点]                        │
   │ 执行工具，把结果"Observation"      │
   │ 追加回对话历史                     │
   └──────────（回到 model 再思考）─────┘

   Start ──→ model ──→ route ──→ tool ──→ model ──→ ...（循环，最多 8 步）──→ End
```

### 4.3 ReAct：Thought → Action → Observation 循环

**ReAct**（Reasoning + Acting，推理 + 行动）是最经典的 Agent 范式。每个循环做三件事：

| 环节 | 英文 | 干什么 | 例子 |
|---|---|---|---|
| 思考 | Thought | 模型想"我该怎么回答" | "用户问时间，我需要查一下" |
| 行动 | Action | 模型决定调用某个工具 | `{"tool": "get_current_time", "args": {}}` |
| 观察 | Observation | 代码执行工具，把结果给回模型 | "Observation: 2026-09-28 16:30" |
| （再思考） | — | 模型看到结果，给出最终回答 | "现在是 2026 年 9 月 28 日 16:30" |

真实一次对话的轨迹（Gradio 界面里能看到）：

```
💡 思考/回答：帮我算 2*(3+4)
🔧 调用工具 calculator，参数：{'expression': '2*(3+4)'}
📊 工具返回：2*(3+4) = 14
💡 思考/回答：2*(3+4) = 14，计算完成。
```

### 4.4 为什么要用"Prompt 模式"而不是模型原生工具调用

大模型通常支持"原生 tool calling"（模型输出一个特殊结构，框架直接解析成工具调用）。
但本项目部署环境的 **vLLM 0.8.5 不支持 Qwen 的原生工具调用解析器**（启动参数 `--tool-call-parser qwen` 直接报错，可选列表里没有 qwen）。

所以采用经典 ReAct 的 **Prompt 模式**：
1. 把工具的 JSON Schema（每个工具叫什么、有哪些参数）写进**系统提示词**；
2. 模型输出一行 JSON：`{"tool": "calculator", "args": {"expression": "2*(3+4)"}}`；
3. **代码**用正则 + `json.loads` 解析这行 JSON，再执行对应工具；
4. 工具结果以 `Observation: ...` 追加回对话历史。

好处：不依赖模型原生能力，任何模型都能跑；对 7B 小模型的输出格式也更容易控制。

### 4.5 工具集（agent/tools.py）

| 工具名 | 干什么 | 安全设计 |
|---|---|---|
| `calculator` | 计算数学表达式 | **AST 白名单**：把表达式解析成语法树，只允许数字/四则运算/括号/白名单数学函数，从结构上拒绝任何可执行代码 → 免疫注入攻击 |
| `get_current_time` | 返回当前日期时间（UTC+8） | 只读，无副作用 |
| `fetch_url` | 抓取网页并转成纯文本 | 只读；抓取失败返回错误信息，让模型自行判断 |

全部**真实可用、无需外部 API Key**——这是项目强调的点（不依赖任何付费服务）。

### 4.6 多轮对话记忆（MemorySaver）

没有记忆的 Agent 每轮都是"失忆"的。本项目用 LangGraph 的 **MemorySaver + checkpointer**：
- 每个会话有一个 `thread_id`（线程 ID），状态按它存档；
- `AgentState.messages` 字段用 `Annotated[list, operator.add]` 声明**追加 reducer**——每轮新消息自动累加进历史，不会覆盖上一轮；
- 所以第二轮问"我第一个问题是什么"，模型/代码能看到第一轮的内容。

### 4.7 对话指代问题的"兜底"设计

测试中发现：问"上一个问题是什么/刚才问的什么"这类问题时，7B 模型**倾向乱调工具**（曾出现它去抓网页搜"your last question"的场面）。

解决办法是**两层兜底**：
1. **规则快路径**：检测到"第一个问题 / 第 N 个问题 / 上一个问题 / 再上一个问题 / 某问题的上一个问题"→ 直接从记忆历史里提取对应问题回答，**不消耗模型推理**；
2. **智能兜底**：规则没匹配到但明显在问历史（如"你记得我之前问过什么吗"）→ 走一个**禁工具**的推理回合，让模型只基于对话历史回答。

效果：指代类问题答得又快又稳，且不会误调工具。

### 4.8 vLLM：把微调模型变成线上服务（agent/serve_vllm.sh）

**vLLM** 是目前工业界最流行的大模型推理服务框架，核心优势：**PagedAttention 显存管理 + 高吞吐**，还支持**动态挂载 LoRA**。

部署链路：

```
Qwen2-7B 基座（models/Qwen2-7B-Instruct，15GB）  ┐
                                                  ├─→ vLLM 启动 → OpenAI 兼容 API
LoRA adapter（output/lora-qwen2/final，77MB）    ┘      （端口 8000）
                                                          │
                                                          ▼
LangChain ChatOpenAI 客户端（agent/llm.py）──→ Gradio 界面（端口 7861）
```

关键参数说明：
- `--served-model-name qwen2-lora`：base 模型的对外名称；
- `--lora-modules lora1=output/lora-qwen2/final`：挂载 LoRA，模块名 `lora1`；
- **坑**：模块名不能与 served-model-name 同名——否则 vLLM 收到请求时会精确匹配 base 模型，LoRA 等于没挂（表现为模型回答仍是微调前行为，比如把 LoRA 答成 LoRa）。改成 `lora1` 后解决，`agent/llm.py` 的 `LLM_MODEL` 默认值也是 `lora1`。

为什么部署成 API 而不是直接加载模型？——**解耦**：模型服务（vLLM）和上层应用（Agent/Gradio）互相独立，Agent 层换成任何模型只要改一个环境变量；这也是生产环境的常见架构。

### 5.2 agent/ 目录（Agent 升级版）

| 文件 | 作用 | 关键点 |
|---|---|---|
| `tools.py` | **工具集**：定义 calculator / get_current_time / fetch_url 三个工具的实现 + JSON Schema（TOOL_SCHEMAS，供系统提示词渲染） | 计算器用 AST 白名单防注入；所有工具无需 API Key |
| `llm.py` | **LLM 后端工厂**：封装 ChatOpenAI（OpenAI 兼容客户端），默认连本机 vLLM（`http://127.0.0.1:8000/v1`），模型名默认 `lora1`；提供 health_check（探测后端是否在线）；支持环境变量切换 | 换后端/换模型只改环境变量 |
| `agent_react.py` | **核心：LangGraph ReAct Agent**。手写状态机（model 节点 → route 条件路由 → tool 节点 → 循环），Prompt 模式工具协议（解析模型输出的 JSON Action 并执行工具），MemorySaver 多轮记忆，对话指代问题两层兜底，流式输出每一步轨迹 | 整个 Agent 的心脏，500 行内自包含 |

| `gradio_agent.py` | **Gradio Agent 网页界面**：浏览器对话，实时显示 Thought/Action/Observation 轨迹，架构下拉切换（ReAct / DeepAgents），异常容错（出错时显示错误原因而非白屏） | 端口 7861 |
| `serve_vllm.sh` | **AutoDL 一键部署脚本**：安装 vLLM（固定 0.8.5）+ 后台启动 vLLM 服务（挂载 LoRA，端口 8000） | 脚本注释里写清了每个参数的用途和踩过的坑 |
| `requirements-agent.txt` | Agent 依赖清单（langgraph、deepagents、langchain-openai、gradio 等） | 与训练依赖相互独立 |

## 6. 一次对话的完整旅程（端到端）

以用户问"帮我算一下 (23+67)*45"为例：

```
① 用户在浏览器输入问题
        │
② Gradio 界面（agent/gradio_agent.py）把问题交给 stream_react()
        │
③ LangGraph 图启动（agent_react.py）：
   - 从 MemorySaver 取出该会话的历史消息
   - 组装 system 提示词（含工具 Schema + 规则）+ 历史 + 新问题
        │
④ 模型节点：Qwen2-7B + LoRA 收到请求（经 vLLM OpenAI 兼容 API）
   模型思考后输出：{"tool": "calculator", "args": {"expression": "(23+67)*45"}}
        │
⑤ 条件路由：检测到 JSON Action → 进入工具节点
        │
⑥ 工具节点：解析 JSON → 调用 calculator（AST 安全求值）→ 得 4050
   把 "Observation: (23+67)*45 = 4050" 追加进历史
        │
⑦ 回到模型节点：模型看到 Observation，输出最终回答
   "（23+67）×45 = 4050，计算完成。"
        │
⑧ Gradio 界面逐块渲染轨迹并展示，本轮结束；历史已存档，下一轮继续累计
```

## 7. 词汇表

| 术语 | 大白话解释 |
|---|---|
| LLM / 大语言模型 | 会"预测下一个词"的超级接话机器，如 Qwen2 |
| Transformer | 主流大模型的结构，核心是注意力机制 |
| 参数 | 模型里的数字，是"学到的东西"，7B = 70 亿个 |
| token / 词元 | 模型处理文本的基本单位，一个词或半个词 |
| 微调（fine-tune） | 用新数据继续训练模型，改变说话风格/领域能力 |
| LoRA | 只训练"并联的小矩阵"（<1% 参数）的微调方法 |
| 秩（r） | LoRA 小矩阵的大小控制参数 |
| 量化 | 把参数从 16 位压到 4 位省显存，NF4 是精度较好的 4bit 格式 |
| PPL / 困惑度 | 衡量模型对语料"意外程度"的指标，越低越好 |
| Adapter | 微调产出的"增量权重包"，很小，可叠加到基座模型上 |
| Agent | 能自主决定"调用工具 + 继续推理"的 AI 系统 |
| ReAct | 思考→行动→观察 循环的 Agent 范式 |
| LangGraph | 用"图（状态机）"编排 AI 流程的框架 |
| Prompt 模式 | 把工具说明写进提示词、模型输出 JSON、代码解析执行的工具调用方式 |
| AST 白名单 | 把表达式解析成语法树，只放行安全节点，防代码注入 |
| MemorySaver | LangGraph 的记忆组件，按 thread_id 保存会话状态 |
| vLLM | 高吞吐的大模型推理服务框架，支持挂载 LoRA |
| OpenAI 兼容 API | vLLM 提供的接口格式与 OpenAI 一致，客户端可无缝接入 |
| Gradio | Python 网页 UI 框架，几行代码做出聊天界面 |
