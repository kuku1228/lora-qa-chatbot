## 2. 微调配置与参数量

| 项 | 值 | 来源 |
|---|---|---|
| 基座 | Qwen2-7B-Instruct | `config.py` |
| LoRA r / α / dropout | 8 / 16 / 0.05 | `config.py` |
| 注入层 | q,k,v,o,gate,up,down_proj（7 个） | `config.py` |
| 量化 | 4bit NF4 + 双重量化 + bf16 计算 | `2_train_lora.py` |
| 优化器 | 8bit paged AdamW | `2_train_lora.py` |
| batch / 梯度累积 | 1 / 16（等效 16） | `config.py` |
| 学习率 / 调度 | 2e-4 / cosine + 3% warmup | `config.py` |
| 训练轮数 | **实际 1 epoch / 1,116 步** | 训练日志 |
| **可训练参数（精确）** | **20,185,088（约 2,019 万）** |
| **可训练占比（精确）** | **0.265%**（分母为模型结构总参数 7,615,616,512） |
| 单层合计 × 层数 | 720,896 × 28 = 20,185,088 ✓（实测打印印证） |
| 各模块明细（单层） | gate_proj 180,224 / up_proj 180,224 / down_proj 180,224 / q_proj 57,344 / o_proj 57,344 / k_proj 32,768 / v_proj 32,768 |
| PEFT 估算值（对照） | 见 `print_trainable_parameters()` 输出 |

> ⚠️ **踩过的坑**：训练脚本原先把 `sum(p.numel())` 当作模型总参数，但 **4bit 量化后
> 量化层返回的是打包后的低比特张量**，`numel()` 不等于逻辑参数量——实测打出
> `模型总参数 4,373,157,376`，于是占比被算成 `0.4616%`，**偏大 1.74 倍**。
> 已改为按模型结构解析计算（`_true_param_count()`），正确值是 **0.265%**。
> 写简历/文档时用 **0.265%**，不要用 0.4616%。

## 4. 全量微调显存需求对比（`python tools/baseline_fp16.py`，解析计算，不需要 GPU）

| 项 | 值 |
|---|---|
| 全量微调显存需求（解析计算） | fp16 权重 14.2 + 梯度 14.2 + AdamW fp32 动量各 28.4 = **下界 85.1 GB**；含激活约 **98 GB** |
| 本项目 LoRA + 4bit（实测峰值） | **11.40 GB**，占 RTX 3090（23.6GB）的 46.5% |
| 显存倍数差 | 约 **8.6 倍** |
| 采集方式 | 本项目峰值来自 `tools/monitor.py` 采样；全量微调由 `tools/baseline_fp16.py` 解析计算 |

**结论表述（已完成，可直接用于文档）**：

> 全量微调（fp16 + AdamW）显存需求约 98 GB（不含激活值的下界 85.1 GB）——fp16 权重 14.2 GB、
> 梯度 14.2 GB、AdamW fp32 一阶/二阶动量各 28.4 GB，**优化器状态占了大头**。
> 本项目采用 LoRA（只更新 0.265% 参数）+ 4bit NF4 量化 + 双重量化 + 梯度检查点
> + 8bit paged AdamW，**实测训练显存峰值 11.40 GB、占 24GB 卡 46.5%**，
> 单卡即可完成 1 epoch 训练，显存需求相差约 8.6 倍。

## 6. 四组消融（`python ablation.py`）

只在 6 组同题上跑，共 4 组 × 6 题 = 24 个回答，全部在 `output/ablation.md`。

| 组合 | 配置 | 作用 |
|---|---|---|
| A | 原始模型（无 prompt） | 基线 |
| B | 原始模型 + system prompt | prompt 单独的作用 |
| C | LoRA 微调（无 prompt） | 微调单独的作用 |
| D | LoRA 微调 + system prompt | 两者叠加 |

### 逐题判定（已实测，来自 `output/ablation.md`）

| 题目 | A 原始 | B 原始+prompt | C 微调（无prompt） | D 微调+prompt |
|---|---|---|---|---|
| 什么是过拟合？ | 冗长 | 冗长 | 简洁 ✓ | 简洁 ✓ |
| 反向传播原理 | 冗长 | 冗长 | 简洁 ✓ | 简洁 ✓ |
| 列表和元组的区别 | 开头分点铺垫 | 开头分点铺垫 | 直接回答 ✓ | 一句话答完 ✓ |
| 数据库索引 | 冗长 | 冗长 | 简洁 ✓ | 简洁 ✓ |
| 如何缓解梯度消失 | 冗长 | 冗长 | 简洁 ✓ | 简洁 ✓ |
| **LoRA 微调原理** | ❌ "LoRaWAN/低功耗广域网" | ❌ **仍答成"无线通信技术"** | ✅ **答对：机器学习技术** | ✅ 答对 |

### 结论（已实测证实）

> **加了 system prompt 的原始模型（B 组）依然把 LoRA 答成无线通信技术，而不带任何 prompt 的
> 微调模型（C 组）答对了。** 说明"回答简洁"这类输出组织方式可以靠 prompt 影响，
> 但**术语与领域知识的修正只能由参数更新带来** —— 这是选择"做微调"而非"只调 prompt"的实验依据。

补充两点观察（都可写进文档）：

- **prompt 修不好"啰嗦"**：同题下 B 组（有 prompt）仍在铺垫"…但它们之间有以下主要区别："准备分点，
  D 组已是一句话答完。
- **微调风格会盖过 prompt**："数据库索引"一题上，C 组（**无 prompt**）比 B 组（**有 prompt**）更简洁，
  说明简洁风格已写进权重，不再依赖提示词维持。

## 7. Agent 决策评测（`python agent_eval.py --backend openai`）

### 对照基线

| 后端 | 是什么 | 决策准确率 | 误调用率 | 漏调用率 |
|---|---|---|---|---|
| `oracle` | 参考决策器，装置自检 | 100% | 0% | 0% |
| **`openai`** | **vLLM 部署的真实微调模型** | **66.7%** | **27.8%** | **33.3%** |
| `naive` | 故意写坏的规则决策器 | 63.3% | 44.4% | 0% |

### 详细指标（openai 后端实测）

| 指标 | 值 |
|---|---|
| 用例数 | 30 |
| 工具选择正确率 | **66.7%** |
| **决策准确率（工具+参数）** | **66.7%** |
| 应调工具场景准确率 | **58.3%**（7/12） |
| 不应调工具场景准确率 | **72.2%**（13/18） |
| 误调用率 | **27.8%**（5 条） |
| 漏调用率 | **33.3%**（4 条） |
| 错因分布 | 误调用 5 / 漏调用 4 / 工具选错 1 |

### 失败模式（10 条错误可归为四类）

| 类型 | 用例 | 现象 |
|---|---|---|
| 该调不调 | C04 取余、C06/C07/C08 三道时间题、C12 只做第一步 | 自己编答案 |
| 不该调却调 | C22 查 Flask 版本、C23 搜新闻、C30 提取 PDF | 硬套工具 |
| 参数缺失 | C14、C29 | Action 的 `args` 为空 |
| 编造工具名 | C14 → `get_previous_message` | schema 里不存在的工具 |

**分场景准确率为 0% 的四类**（最有信息量）：

- **该调·时间：0/3** —— "现在几点/今天星期几/今天几号"全错，模型自己编时间（幻觉风险最高）
- **多步·工具链：0/1** —— "先算 25*4 再算 300/6"只做了第一步
- **边界·先追问：0/1** —— "帮我算一下那个数"直接调了计算器，没追问
- **边界·超出能力：0/1** —— "提取 PDF 表格"编了个 URL 去调 `fetch_url`

### 结论（如实记录，含归因）

> 自建 30 条工具调用测试集评测微调后的 Agent 决策能力，**决策准确率 66.7%**
> （应调场景 58.3%、不应调场景 72.2%、误调用率 27.8%、漏调用率 33.3%）。
> 作为对照，规则决策器基线 63.3%、装置自检 100%。
>
> **原因**：`alpaca_zh_51k` 是纯文本指令数据，**没有任何"工具观测"轨迹**（Action→Observation→再决策），
> 模型因此学到的是"用文字直接回答"的通用模式——需要外部信息时倾向自己编答案（漏调用 33.3%），
> 能力边界之外又倾向硬套工具（误调用 27.8%）。
>
> **结论**：LoRA 微调能让模型掌握回答风格与领域术语（见 PPL 与消融），
> **但不足以让它学会可靠的工具调用决策边界。瓶颈在数据覆盖，不在微调算法。**
>
> ⚠️ 30 条用例规模很小，只作方向性参考，不足以支撑统计结论。

> 这一结论与另一个项目（工具调用 Agent 评测体系与训练语料优化）互相印证：
> 那边补齐"多步流程/多工具组合"样本后，决策类任务准确率从 31.8% → 95.5%。
